## 背景

実装変更に伴うADR更新作業（影響分析・関連ADR検索・ドラフト作成・命名/ステータス/リンク整合の検証）を自動化したい。
しかし、これらすべてを単一エージェントに持たせると、品質とコストのトレードオフが生じる。

- 探索・検証も含めてすべて高性能モデルで処理するとコストが高い。
- 逆に全処理を軽量モデルに任せると、影響分析やSupersede判断の品質が落ちる。

[Harness Engineering](../agents/openAI_harness_enjineerring.md) の「コンテキストは希少資源」という教訓に基づき、役割ごとに責務とモデルを分離する必要があった。

## 決定

ADR Governanceを以下の3層構造で構成する。

| エージェント | 役割 | モデル | 呼び出し |
|---|---|---|---|
| [adr-governance](../../.claude/agents/adr-governance.md) | オーケストレーター。diff収集・変更種別分類・決定パス判断・ドラフト作成 | opus | メイン |
| [adr-search](../../.claude/agents/adr-search.md) | 変更に関連するADR候補の検索に特化（読み取り専用） | haiku | adr-governanceから |
| [adr-validator](../../.claude/agents/adr-validator.md) | 命名・ステータス・Supersedeリンク整合の検証に特化（読み取り専用） | haiku | adr-governanceから |

コスト制御ポリシーとして以下を定める。

- 深い分析の前に、安価なチェック（`git diff` + ファイル名/ステータス検証）を先に実行する。
- サブエージェントは必要なときのみ呼び出す:
  - `adr-search`: diffがアーキテクチャ/運用に影響し、ADRスコープが**不明な場合のみ**。
  - `adr-validator`: ドラフト**作成後のみ**。
- ユーザーが明示的に求めない限り、同一サブエージェントを1リクエスト中に複数回呼ばない（各1回まで）。

## 代替案

- **単一エージェントで全処理**: 1つのエージェントが検索・ドラフト作成・検証をすべて担う案。プロンプトが肥大化し責務が曖昧になるうえ、軽量化できる検索・検証も高性能モデルで処理することになりコスト効率が悪い。また、サブエージェント分離により「不要なら呼ばない」コスト制御ができなくなるため不採用。

## 影響

- ADR更新は `/adr-governance` スキルまたは `adr-governance` サブエージェント経由で行う運用に統一される。
- 検索・検証はhaikuモデルで実行されるため、ADRスコープが明確な場合のコストを抑えられる。
- adr-search / adr-validator は読み取り専用（Read, Grep, Glob）であり、ADRファイルの編集はオーケストレーターのみが行う。
- GitHub Copilot版（`.github/agents/adr/`）は互換維持のため削除せず並存する。

## 今後の見直しポイント

- サブエージェント呼び出しの「各1回まで」制限が実運用で不足する（複雑なSupersede連鎖等）場合は、上限の見直しを検討する。
- モデル割り当て（opus / haiku）は、検索・検証の精度や利用可能なモデルの変化に応じて再評価する。
