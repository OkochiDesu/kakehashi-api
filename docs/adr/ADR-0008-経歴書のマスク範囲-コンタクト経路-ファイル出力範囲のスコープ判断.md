## 背景

要件定義フェーズで以下3つの未確定事項について、Step1の実装範囲と業務ルールを確定する必要があった（[README.md 8章 2026-06-15の意思決定](../requirements/README.md#8-意思決定ログ)）。

1. マスク済み経歴書（UC-R2）のマスク対象列と、マスク解除の判定ルール
2. UC-M1（エンジニアへのコンタクト）のコンタクト経路（直接コンタクト vs 営業経由）
3. UC-F1（経歴書ファイル出力）の出力対象範囲と出力履歴ログの要否

いずれも「業務ルールの確定」と「Step1/Step2のスコープ線引き」に関わる恒久的な決定であり、実装（テーブル設計・API設計）への影響が大きいため、ADRとして記録する。

## 決定

### 1. マスク済み経歴書（UC-R2）の対象列とマスク解除ルール

マスク対象は `resumes.nearest_station`（最寄り駅）・`resumes.final_education`（最終学歴）の2列に限定し、`visibility_rules.target_category = resume_personal_info` として管理する。`age`（年齢）・`self_pr`・`resume_qualifications`・`resume_projects` はマスク対象外で本人以外にも公開する。

マスクの適用・解除は以下の通り判定する。
- 閲覧者が経歴書の所有者本人（`resumes.account_id` = 閲覧者の `account_id`）の場合: マスクしない。
- 閲覧者が本人以外の場合: `account_roles` 経由で閲覧者が持つロールのいずれかが、`visibility_rules` で `target_category = resume_personal_info` に対し `can_view: true`（例: 管理者ロール）であればマスクしない。該当ロールがなければ `nearest_station` / `final_education` をNULL化（または非選択）して返す。

ロール別の詳細な可視範囲（どのロールが何を閲覧可能か）は「決定4」を参照。

### 2. UC-M1のコンタクト経路はStep1ではエンジニア間直接コンタクトのみ

Step1ではエンジニア間の直接コンタクト（Googleメッセージ起点、本リポジトリ側での永続化なし）のみとし、営業担当を介する運用・`contacts` テーブルは対象外とする。営業経由ルーティングの検討はStep2（AIレコメンド検討時）にまとめて行う。

### 3. UC-F1の出力対象は経歴書のみ、出力履歴ログは設けない

経歴書ファイル出力（UC-F1）の出力対象は経歴書（`resumes` / `resume_qualifications` / `resume_projects`）のみとし、星取表（`user_skills`）は出力対象外とする。出力履歴（誰がいつ誰の経歴書を出力したか、`resume_export_logs` 等）はStep1では設けない。

対象ファイル: [docs/requirements/data-models.md](../requirements/data-models.md)（1章・4章・5章） / [docs/requirements/ui-flows.md](../requirements/ui-flows.md)（2章・4章・5章）

### 4. ロール別可視範囲（`visibility_rules` 初期データ方針）

Step1で定義するロールは `general`（一般エンジニア）・`sales`（営業）・`admin`（管理者）の3種類とし（[data-models.md 1章](../requirements/data-models.md#1-認証アカウントコンテキスト) の `roles.code`）、`visibility_rules` の初期データは以下の通りとする。

| ロール (`roles.code`) | `target_category` | `can_view` | 経歴書編集権限 | 説明 |
|---|---|---|---|---|
| `general` | `resume_personal_info` | false | 自分の経歴書のみ | 一般エンジニアは最寄り駅・最終学歴をマスクして閲覧 |
| `sales` | `resume_personal_info` | true | 不可 | 営業は全項目閲覧可・編集は不可 |
| `admin` | `resume_personal_info` | true | 全経歴書 | 管理者は全項目閲覧・全経歴書編集可 |

所有者本人は `visibility_rules` による判定よりも優先してマスクしない（決定1の判定ロジック参照）。Step1では上記3ロール・1カテゴリの組み合わせのみを想定し、初期データをマイグレーションスクリプトで投入する。将来 `target_category` が増える場合は `visibility_rules` に行を追加する運用とし、本テーブル構造の変更は不要。

## 代替案

### 1. マスク範囲について

#### 代替案A: 経歴書全体を本人以外に非公開とする
- 長所: 個人情報保護が最大化される
- 短所: 「検索画面」「エンジニアページ」での経歴書活用（主要機能の1つ）が成立しない。星取表との連携（ADR-0007）の前提も崩れる。

#### 代替案B: マスク対象列をロール別に細かく設定可能にする（汎用的な列単位制御）
- 長所: 将来的な個人情報項目の追加・変更に柔軟に対応できる
- 短所: Step1で必要な範囲（最寄り駅・最終学歴の2列）に対して設計・実装コストが過大。`visibility_rules` の `target_category` という区分単位の仕組みで2列をまとめて扱う現方針で十分。将来列が増えた場合は `target_category` の追加で対応可能。

### 2. コンタクト経路について

#### 代替案A: Step1から営業経由ルーティングを実装する
- 長所: 「エンジニア間の直接コミュニケーションが難しいケース」に最初から対応できる
- 短所: `contacts` テーブル・営業担当の紐付け管理・ルーティングロジックの設計が必要になり、Step1のスコープ（経歴書のWeb化・星取表・検索画面）に対して付随的な機能の比重が大きくなる。AIレコメンド（Step2）導入時にコンタクト経路を再設計する可能性が高く、先行実装が手戻りになるリスクがある。

### 3. ファイル出力範囲について

#### 代替案A: 星取表も出力対象に含める
- 長所: 1ファイルでエンジニアの情報を網羅できる
- 短所: 主要機能として経歴書と星取表は別ユースケース（UC-R系/UC-S系）として整理されており、出力フォーマット（Excel/PDF）の設計が複雑化する。Step1では経歴書出力（UC-F1）のみが要求されている。

#### 代替案B: 出力履歴ログ（resume_export_logs）をStep1で設ける
- 長所: 誰がいつ誰の経歴書を出力したかを追跡できる（セキュリティ・利用状況分析の観点）
- 短所: Step1の主要機能に対する付随機能であり、テーブル追加・記録処理のコストに対して優先度が低いと判断。利用状況分析のアイデアは [docs/TODO.md](../TODO.md) の「利用状況分析（Step2 AIレコメンド連携）」に記録済み。

## 影響

- `visibility_rules` テーブル（[data-models.md 1章](../requirements/data-models.md#1-認証アカウントコンテキスト)）は、経歴書のマスク制御（UC-R2）と権限変更（UC-A6）の両方に使われる共通の可視性制御テーブルとなる。
- UC-M1関連で `contacts` テーブル等は作成しない。Step2でのAIレコメンド連携検討時に、コンタクト履歴・営業担当の紐付けを管理するテーブルを別途検討する。
- UC-F1関連で `resume_export_logs` 等は作成しない。星取表の出力ニーズが将来生じた場合は、別途要件定義・ADRが必要。

## 今後の見直しポイント

- マスク対象列が増える場合（個人情報項目の追加等）、`visibility_rules.target_category` への追加で対応するか、本ADRを更新して列単位制御の仕組みを再検討する。
- Step2でAIレコメンド機能を検討する際、UC-M1の営業経由ルーティングを実装する場合は新規ADRを作成し、本ADRの決定2をSupersedeする。
- 利用状況分析・出力履歴のニーズがStep2で具体化した場合、本ADRの決定3を見直す。
- **氏名フィールドのイニシャル方針（カラム設計未決定）**: 経歴書上の氏名はイニシャル形式を必須とする方針であるが、具体的なカラム設計は未確定。`accounts.name`（Googleプロフィールの `name` をそのまま保持）にイニシャル入力を強制するか、`resumes` に `display_name` 列を別途追加するかは実装フェーズで決定する（前者はアカウント全体への副作用、後者はテーブル追加コストとのトレードオフ）。決定時は本ADRを更新する。
