## 背景

REST API の URL 設計においては `/api/v1/accounts` のようにバージョンプレフィックスを付ける慣習がある。バージョンプレフィックスの主な目的は「破壊的変更が必要になったとき、旧バージョン（`v1`）と新バージョン（`v2`）を並走させ、クライアントが段階的に移行できるようにする」ことである。

kakehashi-api は社内システムであり、フロントエンドとバックエンドを同一チームが管理する。破壊的変更が必要になった場合、フロントエンドとバックエンドを同時に切り替えられるため、バージョン並走期間が不要である。

## 決定

API パスにバージョンプレフィックス（`/v1/` 等）を含めない。

パス形式: `/api/{リソース}`（例: `/api/accounts`, `/api/auth/google/callback`）

## 代替案

### 代替案A: `/api/v1/` プレフィックスを付ける（不採用）

- 長所: 外部公開 API や複数の外部クライアントが存在する場合、後方互換を保ちながら段階的に移行できる。
- 短所: フロントエンドとバックエンドを同一チームが管理する社内システムでは、破壊的変更時はフロントエンドも同時に切り替えられるため、バージョン並走期間が不要。将来的に外部公開が必要になった場合はその時点で再設計すれば十分。

## 影響

- `docs/design/api/account-role.md` の全エンドポイントパスは `/api/` 形式で記述する。
- Controller の `@RequestMapping` は `/api/accounts` 等のバージョンなし形式で実装する。
- 将来、外部公開や複数クライアント対応が必要になった場合は本ADRを Supersede し、バージョニング方式を再設計する。

## 今後の見直しポイント

- 外部クライアント（サードパーティ連携・パートナー企業等）への API 公開が決まった場合はバージョニング方式を再検討する。
