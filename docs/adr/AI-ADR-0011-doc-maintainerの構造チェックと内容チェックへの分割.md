## 背景

[AI-ADR-0003](AI-ADR-0003-doc-maintainerの読み取り専用チェッカー設計.md) では、`docs/` 配下の整合性チェックを単一の `doc-maintainer` エージェントに集約し、「チェック対象を増やす場合は新規エージェントを作らず doc-maintainer のチェック項目を拡張する」方針を採用していた。

しかし `docs/` の規模拡大に伴い、この単一エージェント方式に以下の非効率が顕在化した。

- コミット前に毎回呼び出すチェックが重くなってきた（全項目を常に実行するため）。
- コミット前に必要な「構造チェック」（索引・リンク整合性・`.claude/`構成・ToC）と、定期的に行えば十分な「内容チェック」（ADR整合・鮮度・exec-plans・design-docs・TODO実行可能性・ナビゲーション指標）は性質が異なるにもかかわらず、常にまとめて実行していた。

構造チェックは機械的・高速で、コミットのたびに走らせる価値があるのに対し、内容チェックは判断を伴い相対的に重く、PR作成前やユーザー明示指示時に走らせれば十分である。実運用でこの差が顕在化したため、役割を分割する。

## 決定

`doc-maintainer` を2つの読み取り専用エージェントに分割する。

- **doc-maintainer-structure**: 索引・リンク整合性・`.claude/`構成との一致・ToC（目次）の有無をチェックする。軽量・高速。
- **doc-maintainer-content**: ADR整合性・鮮度・exec-plans・design-docs・TODO実行可能性・ナビゲーション指標をチェックする。判断を伴い相対的に重い。

呼び出しポリシー:

- **コミット前**: `doc-maintainer-structure` のみを diff スコープで呼び出す（軽量・高速）。
- **定期チェック（PR作成前 / ユーザー明示指示時）**: `doc-maintainer-structure` と `doc-maintainer-content` を**並列で**呼び出す。
- メインAIがオーケストレーターとして両エージェントを呼び出し、結果を統合する。

両エージェントとも [AI-ADR-0003](AI-ADR-0003-doc-maintainerの読み取り専用チェッカー設計.md) の読み取り専用原則（ツールを Read / Grep / Glob に限定し、Write / Edit を付与しない）を引き継ぐ。検出と修正の責務を分離するヒューマンインザループ方針は維持する。

旧 `doc-maintainer`（全項目フルチェック）はレガシーとして当面残すが、上記2エージェントの並列実行を推奨とする。

## 代替案

1. **現状維持（単一エージェント継続）**: `docs/` 規模の拡大に伴い、コミット前チェックの重さが悪化する一方であり、AI-ADR-0003 が想定していた「チェック項目を拡張し続ける」運用が立ち行かなくなる。
2. **チェック項目を間引く**: コミット前の負荷は下がるが、網羅性が下がり陳腐化・不整合を見逃すリスクが高まる。HITL土台の信頼性を損なう。
3. **2エージェントに分割してメインAIが並列オーケストレーション（採用）**: コミット前は構造チェックのみで高速化しつつ、定期チェックでは両者を並列実行して網羅性も担保する。チェックの性質（機械的/判断的、高頻度/低頻度）に応じて責務を分けられる。

## 影響

- コミット前チェックは `doc-maintainer-structure` のみとなり、軽量・高速化する（[CLAUDE.md](../../CLAUDE.md) の「commit運用」doc-maintainerチェック項に反映済み）。
- PR作成前・ユーザー明示指示時は両エージェントを並列で呼び出す運用とする。
- メインAIが両エージェントの呼び出しと結果統合のオーケストレーターを担う。
- 両エージェントとも読み取り専用であり、いつ・何度呼び出しても安全（AI-ADR-0003 の安全性を継承）。
- [docs/agents/README.md](../agents/README.md) のエージェント一覧・AI-ADR索引、[AGENTS.md](../../AGENTS.md) のサブエージェント一覧を本決定に整合させる。
- 旧 `doc-maintainer` はレガシーとして残すため、エージェント定義・索引上は3エージェントが併存する状態になる。

## 今後の見直しポイント

- レガシーの `doc-maintainer`（フルチェック版）が実運用で使われなくなった場合、定義の整理・廃止を検討する。
- 分割後も特定のチェック項目（例: 鮮度チェック）の負荷が突出する場合、内容チェックのさらなる細分化または間引きの可否を再検討する。
