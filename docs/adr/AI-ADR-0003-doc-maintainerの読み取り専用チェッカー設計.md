## 背景

`docs/` 配下のドキュメントは、索引漏れ・リンク切れ・ADR命名規則違反・陳腐化などの不整合が蓄積しやすい。
これらを継続的にチェックするエージェントが必要になった。

設計上の選択肢として、エージェントに自動修正（Write/Edit）権限を与えるかどうかが論点になった。
[Harness Engineering](../references/harness-engineering/openai-harness-engineering.md) の「ドキュメント整備エージェント」の考え方を、安全な形で導入する必要があった。

## 決定

[doc-maintainer](../../.claude/agents/doc-maintainer.md) を読み取り専用のチェッカーとして設計する。

- ツールを **Read / Grep / Glob のみ** に限定し、Write / Edit 権限は付与しない。
- 出力はチェック結果（**OK** / **要対応リスト**）と具体的な修正案のみとし、ファイルの作成・編集・削除は行わない。
- 実際の修正は、人間またはメインAIが doc-maintainer の報告を受けて行う。

チェック項目には、索引の網羅性・リンク整合性・ADR整合性・鮮度・exec-plans/design-docs整合性・TODO実行可能性・ナビゲーション指標の閾値・`.claude/`構成との整合性・ToCの有無などを含める（具体項目はエージェント定義を参照）。

## 代替案

- **Write / Edit 権限を付与して自動修正**: doc-maintainer が検出した不整合をその場で修正する案。修正の妥当性を人間が確認する前にドキュメントが書き換わるため、誤った自動修正（リンクの取り違え・索引の誤更新）がそのまま入るリスクがある。「まずは安全な読み取り専用から導入する」方針に反するため不採用。

## 影響

- doc-maintainer は副作用を持たないため、いつ・何度呼び出しても安全である。
- ドキュメント修正のヒューマンインザループが保たれる（検出と修正の責務を分離）。
- チェック対象を増やす場合は、新規エージェントを作らず doc-maintainer のチェック項目を拡張する方針（エージェント数を増やさず「docs/全体の整合性チェック」という役割に一貫させる）。

## 今後の見直しポイント

- 読み取り専用運用で「検出はできるが修正が滞る」状況が頻発する場合、限定的な自動修正（明確に機械的な索引更新など）の導入可否を再検討する。
