## 背景

`code-reviewer` と `test-reviewer` の出力フォーマットを見直した際、「問題があった項目だけ列挙する」形式では、エージェントがチェックをスキップしても出力に表れないことが判明した。

例えば `## 確認済み項目（問題なし）` に一部の項目だけ挙げても、残りをチェックしたかどうかが判断できない。最終ゲートとして機能するためには「全項目をチェックしたこと」を出力で証明できる形式が必要である。

## 決定

`## チェック項目` または `## チェックリスト` セクションを持つすべてのエージェント定義ファイルに、以下のルールを適用する。

**全チェック項目を必ず出力に列挙し、各項目にステータスを明記する。**

エージェント種別によってステータス表記を使い分ける：

| 種別 | 出力形式 | ステータス値 |
|---|---|---|
| レビュー系（APPROVED/REQUIRES_CHANGES を返す） | `PASS / FAIL / SKIP` | PASS: 問題なし / FAIL: 問題あり / SKIP: 対象外 |
| チェッカー系（OK/要対応/REQUIRES_FIX を返す） | `OK / 要対応 / SKIP` | OK: 問題なし / 要対応: 問題あり / SKIP: 対象外 |

いずれの種別も「チェックを省略しても出力に現れない」リスクを排除するため、全項目列挙を必須とする。

条件付きチェック項目（例: 楽観ロックは update 操作を含む場合のみ、MyBatis は Mapper diff がある場合のみ）は `SKIP` を使って対象外であることを明示する。

## 代替案

1. **問題項目のみ列挙する（従来方式）**: レビュー結果が簡潔になるが、チェック漏れが出力に現れない。最終ゲートとしての信頼性が低い → 却下
2. **確認済み項目のみ列挙する**: 上記と同じ問題。FAIL 項目の見落としリスクがある → 却下
3. **エージェントに内部メモとして記録させる**: 出力に残らないため人間が確認できない → 却下

## 影響

- レビュー系（`code-reviewer` / `test-reviewer`）およびチェッカー系（`design-impl-checker` / `doc-maintainer-structure` / `doc-maintainer-content` / `src-doc-maintainer` / `adr-validator`）の出力が長くなる
- チェック漏れが出力上で即座に識別できるようになる
- 新たなチェックリスト出力を持つエージェントを追加する際は、このパターンに従って出力フォーマットを設計する
- `SKIP` の活用により「差し引きの適用範囲」が明示され、不要な FAIL / 要対応 を防げる

## 今後の見直しポイント

- チェック項目数が増えて出力が長すぎる場合、カテゴリ単位の集約（`KDoc品質: 全PASS`）を許容するかを再検討する
- 新たなチェックリスト出力を持つエージェントを追加するときにこのパターンを適用する
