## 背景

exec-plan 0017 の一環として、Qiita 記事「Claude Code のセキュリティ設定 10 選」を参照し、このリポジトリに未適用のセキュリティ設定項目について適用有無を判断した。

検討対象としたのは以下の3項目である。

- `allowUnsandboxedCommands: false`
- ネットワークホワイトリスト
- PreToolUse フックによる Bash 事前検証

いずれも「適用するか・見送るか」を判断し、その理由を記録しておかないと、将来同じ項目を再検討する際に「なぜ今は入れていないのか」が辿れなくなる。記事を読むたびに同じ棚卸しを繰り返すことを避けるため、判断結果を AI-ADR として記録する。

## 決定

3項目すべてを **見送る**。それぞれの理由は以下の通り。

### ① `allowUnsandboxedCommands: false`

見送る。`permissions.deny` リストで `rm`・`curl`・`wget`・`find -delete` 等を個別にブロックしており、`allowUnsandboxedCommands` は重複設定になる。deny リストの方が意図が明確で粒度が細かいため、設定を増やすより deny リストを正とする方針を維持する。

### ② ネットワークホワイトリスト

見送る。`deny` リストに `Bash(curl *http*)` / `Bash(wget *)` / `Bash(fetch *http*)` が既に入っており、実質的なインターネットアクセスブロックは実現済み。許可する URL が明確になった段階で改めてホワイトリスト方式への移行を検討する。

### ③ PreToolUse フックによる Bash 事前検証

見送る。deny リストが先に機能するため原則として二重チェックは不要。このプロジェクトでは Claude 自身がコマンドを構築しており、悪意ある迂回（`bash -c 'rm ...'` 形式）は想定しにくい。将来エージェント連鎖が複雑になり、外部入力がコマンドに混入するリスクが高まった場合に再検討する。

## 代替案

- **すべての項目を適用する（belt-and-suspenders アプローチ）**: 多層防御として全項目を入れる。却下理由: 設定の重複は「何がどこで守られているか」の見通しを悪化させ、設定変更時の整合維持コストを上げる。deny リストという単一の正を持つ方が、このリポジトリの規模では安全性と保守性のバランスがよい。

## 影響

- セキュリティ設定の正は `.claude/settings.json` の `permissions.deny` リストに一本化される
- 上記3項目は現時点では `.claude/settings.json` に追加しない
- 将来、許可 URL が明確になる・エージェント連鎖が複雑化する等の状況変化があれば、本 ADR を見直し新規 ADR で方針を更新する
