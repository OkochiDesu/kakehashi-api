## 背景

要件定義フェーズで星取表コンテキスト（[data-models.md 3章](../requirements/data-models.md#3-星取表コンテキスト)）と経歴書コンテキスト（[data-models.md 4章](../requirements/data-models.md#4-経歴書コンテキスト)）のデータモデルを詳細化する過程で、以下2つの論点が生じた。

1. イベントストーミングでは「スキルの保有登録」と「スキルへのレベル設定」が別イベントとして識別されていたが、1ユーザー・1スキル項目に対しレベルは最大1つ（1:1）であり、`user_skills` と `user_skill_levels` を別テーブルに分けるとUC-S3/UC-S4の実装・整合性管理が複雑になる。
2. 経歴書の案件経歴（`resume_projects`）の使用言語・ツールを当初 `text[]` + GINインデックスの自由入力で設計していたが、星取表のスキルマスタ（`skill_master_items`）と語彙が重複・不整合になりうる。さらにイベントストーミング上の論点「経歴書を更新するタイミングで星取表にスキルを反映できないか？」が未解決だった。

これらは [README.md 8章 2026-06-15の意思決定](../requirements/README.md#8-意思決定ログ)（user_skills統合、星取表マスタの共通化、resume_project_skills新設、経歴書→星取表連携）として確定した。

## 決定

### 1. user_skills と user_skill_levels の統合

`user_skills` と `user_skill_levels` を1テーブル（`user_skills`）に統合する。`user_skills.level_master_item_id`（FK → `level_master_items.level_master_item_id`）をnullable列とし、「スキルのみ登録・レベル未設定」を `level_master_item_id = NULL` の行で表現する。`(account_id, skill_master_item_id)` の組で一意とする。

これに伴いUC-S3（星取表スキル編集）とUC-S4（星取表レベル編集）を統合し、UC-S3「星取表（スキル・レベル）編集」とする。

### 2. スキル・レベルマスタの共通化

`skill_categories` / `skill_master_items` / `level_categories` / `level_master_items`（3章）を、星取表専用ではなく経歴書（4章）からも参照される共通のスキル・レベルマスタとして位置づける。テーブル名・配置章は変更しない。

### 3. resume_projects.languages_tools の廃止と resume_project_skills の新設

`resume_projects.languages_tools`（`text[]` + GINインデックス）を廃止し、案件経歴×使用スキルの中間テーブル `resume_project_skills`（`resume_project_id` × `skill_master_item_id`、`(resume_project_id, skill_master_item_id)` の組で一意）を新設する。経歴書検索（案件名×言語、[quality-standards.md 1章](../requirements/quality-standards.md#1-機能適合性functional-suitability)）は `resumes` / `resume_projects` / `resume_project_skills` / `skill_master_items` のJOINで行う。

### 4. 経歴書保存時の星取表への自動連携

UC-R1（経歴書保存）後、`resume_project_skills` に登録された各 `skill_master_item_id` について、保存者本人の `user_skills` に未登録であれば `level_master_item_id = NULL` の行をUPSERTする。既存の `user_skills` 行（レベル設定済みを含む）は上書きしない。

- 経歴書保存（UC-R1）自体は新規スキル検出の有無に関わらず即時完了させる（保存処理をブロックしない）。
- 保存後、新規追加された `user_skills` 行（`level_master_item_id = NULL`）がある場合は、レベル入力を促す確認ダイアログを表示する（スキップ可）。入力された場合はその場で `level_master_item_id` を更新し、スキップした場合はNULLのまま残す。
- `level_master_item_id = NULL` の行は「レベル未設定」として、マイページ等で件数バッジ等のリマインダー表示を行い、星取表の陳腐化を防ぐ。レベルの設定・変更は星取表編集（UC-S3）で行う。

対象ファイル: [docs/requirements/data-models.md 3章・4章](../requirements/data-models.md#3-星取表コンテキスト) / [docs/requirements/ui-flows.md 0章・3章・4章](../requirements/ui-flows.md#0-全体画面構成)

## 代替案

### 代替案A: user_skills / user_skill_levels を別テーブルのまま維持する

- 長所: 「スキル保有」と「レベル設定」のイベントを別テーブルとして明確に分離できる
- 短所: 1:1関係であるため、2テーブル間の整合性管理（レベル設定時に対応するuser_skills行が存在するかのチェック等）が常に必要になり、UC-S3/UC-S4が分裂したまま実装・UIが複雑化する。1:1なのでテーブルを分ける利点が小さい。

### 代替案B: resume_projects.languages_tools（text[] + GIN）を維持する

- 長所: 自由入力のため、マスタに存在しない言語・ツールも記録できる。実装もシンプル。
- 短所: 星取表のスキルマスタと語彙が重複・不整合になり、経歴書↔星取表の連携（決定4）が成立しない。「案件名×言語」検索の精度も自由入力テキストに依存し低下する。

### 代替案C: 経歴書→星取表の自動連携を行わない（手動登録のみ）

- 長所: 経歴書保存処理がシンプルになり、UPSERTやダイアログ表示のロジックが不要
- 短所: 経歴書で使用したスキルが星取表に反映されず、星取表の陳腐化（実態との不整合）が解消されない。イベントストーミングで識別された論点（経歴書更新時の星取表反映）に対応できない。

## 影響

- `user_skill_levels` テーブルは作成しない。`user_skills.level_master_item_id` はnullableかつFK制約付き。
- `skill_master_items` / `level_master_items` の変更（アーカイブ等）は星取表だけでなく経歴書側の `resume_project_skills` 経由の参照にも影響するため、運用変更時は両コンテキストへの影響を確認する必要がある。
- 経歴書保存（UC-R1）のCommand処理に、`user_skills` へのUPSERT処理（副作用）が追加される。トランザクション設計・失敗時のロールバック範囲は実装フェーズで確定する。
- マイページ画面（[ui-flows.md 0章](../requirements/ui-flows.md#0-全体画面構成)）に「レベル未設定」件数のリマインダー表示が追加される。

## 今後の見直しポイント

- 経歴書保存時のUPSERT処理のパフォーマンス（案件経歴数・スキル数が多い場合のレイテンシ）が問題になった場合、非同期化を検討する。
- スキルマスタのアーカイブ（`status`）が経歴書側 `resume_project_skills` に与える影響（アーカイブ済みスキルを使用した過去の案件経歴の表示方法）は、実装フェーズで詳細化が必要になった場合に本ADRを更新する。
- 検索条件・利用者属性・星取表のスキル傾向のログ化（Step2のAIレコメンド連携検討）は、[docs/TODO.md](../TODO.md)の「利用状況分析（Step2 AIレコメンド連携）」を参照する。
